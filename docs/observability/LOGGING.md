# Logging standard — YIL-12

## Library

`pino` for application logs. One shared instance from `src/lib/logger.ts`.
Use it directly (`logger.info(...)`) — do not wrap it.

## Output

- **Production**: JSON lines on stdout. The container runtime / log drain
  ships them. One event per line.
- **Development**: `pino-pretty` when `LOG_PRETTY=true`. Set in `.env.local`,
  not committed.

## Levels

| Level   | When to use                                                              |
|---------|--------------------------------------------------------------------------|
| `trace` | Reserved for hot-path debug. Off in prod.                                |
| `debug` | Verbose info useful while developing. Off in prod.                       |
| `info`  | **Default.** Request lifecycle, state transitions, successful operations.|
| `warn`  | Recoverable failures: retried, fallback path used, deprecated API called.|
| `error` | Handled exceptions. Always include `err` (the Error object) and `requestId`.|
| `fatal` | Process is about to die. The only place this should fire is `process.on('uncaughtException')`. |

Default level is controlled by `LOG_LEVEL` env var (`info` by default).

## Required fields on every event

```jsonc
{
  "level": "info",
  "time": "2026-07-11T05:01:23.456Z",
  "service": "yil-marketplace",
  "env": "production",
  "sha": "abc1234",
  "msg": "request completed",
  // context-specific fields:
  "requestId": "01HX...",
  "route": "/api/listings",
  "method": "GET",
  "status": 200,
  "durationMs": 42
}
```

- `requestId` is generated by `src/lib/observability/request-log.ts` at the
  edge of every request and threaded through. Use it to grep across logs.
- `sha` is the deployed commit SHA. Set in `next.config.mjs` from
  `VERCEL_GIT_COMMIT_SHA` or `GITHUB_SHA`.
- `service` and `env` come from the logger, not the call site.

## Redaction

Never log these directly. They are stripped by `src/lib/observability/redact.ts`
on the `LOG_REDACT_PATHS` env var (comma-separated paths):

- `password`, `*.password`
- `*.secret`, `*secret*`
- `token`, `*.token`, `*token*`
- `authorization`, `cookie`, `set-cookie`
- `credit_card`, `*.credit_card`, `*.cc`
- `*.ssn`, `*.tax_id`
- `session`, `*.session`

If a field needs to be in the log for debugging, log it under a clearly marked
`_unsafe` key — redaction does not strip those, and the postmortem will catch
the leak.

```ts
logger.info({ userId, _unsafe: { dbCreds } }, "connection retry");
```

## What NOT to log

- Full request bodies (size + content-type is enough for triage).
- Authorization headers (already redacted).
- Listing photos, user-uploaded content.
- Anything in the `X-Forwarded-*` headers (high spam signal).

## Conventions

- One log line per logical event. Do not split a single operation across
  multiple info events — use a single event with structured fields.
- Use `logger.child({ route, method })` to bind context for a request.
- Use `logger.info({ event: "listing.created", listingId }, "listing created")`
  so dashboards can group by `event`.

## Local development

```bash
LOG_PRETTY=true LOG_LEVEL=debug npm run dev
```

## What to grep for in an outage

```bash
# All errors in the last hour
level=error

# A specific request across services
requestId=01HX...

# All events for one incident type
event=payment.failed

# Slow requests
durationMs>1000
```

The aggregator you ship logs to (Better Stack / hosted Grafana Loki / etc.)
must support these queries — verify before relying on it during an incident.
